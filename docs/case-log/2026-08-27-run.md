# 案例记录：补充小白部署、优化与团队协作指南

## 目标

为第一次接触 Docker、Git 和 GitHub 的学习者提供可执行的中文资料，并正式交付到公开仓库。

成功标准：

- 小白可从安装 Docker 到首次登录逐步完成本地部署；
- 优化建议包含优先级、收益、成本、风险与验收信号；
- GitHub 协作覆盖成员、Issue、分支、提交、PR、CI、Review、冲突、合并和发布；
- Markdown 内部链接、本地综合检查、PR 检查和最终 main 检查全部通过。

风险等级：低。业务代码、数据库和部署配置均不在本轮修改范围。

## 交付合同

合同状态：已由仓库所有者批准。

为什么要做：

让第一次接触 Docker、Git 和 GitHub 的学习者能够独立启动 Aurora，并为后续演进和团队协作提供可执行依据。

验收标准：

1. 部署指南必须包含前置条件、逐步命令、每步检查点、危险操作和故障排查；
2. 优化表必须明确哪些是未来建议，不得把建议写成已实现；
3. 协作指南必须与现有模板、CODEOWNERS 和 CI 一致；
4. 公开仓库合并必须经过 PR 和远端 Actions。

禁止的捷径：

- 只写“运行 Docker 即可”；
- 堆砌技术名词但不给成本、风险和验收方式；
- 建议共享账号、直接修改 main、强推或跳过测试；
- 在没有服务器、域名和证书时宣称公网部署完成。

回滚方式：文档使用独立提交和普通 revert，不改写历史。

## 意外与处理

1. 系统 `python3` 不支持 Harness 使用的 `Path.write_text(..., newline=...)` 参数。没有修改全局 Skill，改用 Codex bundled Python 后完成运行。
2. Git 教学文档原样展示冲突标记时，被 `git diff --check` 当成真实未解决冲突。改用全角符号展示，并在正文说明真实文件使用半角标记。

## 可复用经验

- 面向小白的部署文档必须同时写前置条件、检查点、数据边界和排错路径；
- “未来建议”和“当前已实现”必须分开；
- 教学内容本身也要通过仓库现有的静态检查；
- 文档变更同样适合用 Issue/分支/PR/CI 的完整流程验证。
