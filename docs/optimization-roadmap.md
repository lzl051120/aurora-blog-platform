# Aurora Blog Platform 后续优化建议表

> 本文是**未来优化参考**，不是已完成功能清单。当前已验证范围仍是本地 Docker 部署、现有安全机制和当前测试报告中的证据。
>
> 建议先解决 P0，再处理 P1；不要为了“技术看起来高级”一次引入过多基础设施。

## 优先级定义

| 级别 | 含义 | 建议处理时间 |
|---|---|---|
| P0 | 公网部署或真实用户使用前必须解决 | 上线前 |
| P1 | 明显改善稳定性、性能和维护效率 | 首个迭代周期 |
| P2 | 随用户量和内容量增长再投入 | 有真实指标后 |
| P3 | 探索型或差异化能力 | 核心体验稳定后 |

## 总体优化建议表

| 编号 | 优先级 | 方向 | 当前基础 | 建议方案 | 预期收益 | 成本/风险 | 可验收信号 |
|---|---|---|---|---|---|---|---|
| O-01 | P0 | HTTPS | 本地 HTTP，`COOKIE_SECURE=false` | 公网入口使用受信任证书，生产环境设置 `COOKIE_SECURE=true`，强制 HTTP 跳转 HTTPS | 防止 Cookie 和内容被窃听 | 需要域名、证书和反向代理配置 | HTTPS 扫描通过；Cookie 带 `Secure`；HTTP 自动跳转 |
| O-02 | P0 | 密钥管理 | 本地 `.env` 随机生成且不进 Git | 生产使用平台 Secret、Vault 或云密钥管理；建立定期轮换和泄露响应流程 | 降低密码进入代码、日志或聊天记录的风险 | 轮换时需协调数据库、Redis 和应用 | Git 历史无密钥；旧密钥失效；服务使用新密钥正常 |
| O-03 | P0 | 生产配置 | 单一 Compose 面向本地验收 | 增加明确的 production profile，关闭非必要文档/Actuator 暴露，限制管理端来源 | 减少攻击面和配置误用 | 多环境配置需要维护 | 生产配置审查通过；外网无法访问内部运维端点 |
| O-04 | P0 | 备份灾备 | 已有本地备份恢复脚本 | 自动定时备份、加密、异地保存、保留周期和季度恢复演练 | 防止单机损坏导致数据永久丢失 | 存储成本；必须验证备份可恢复 | 恢复时间 RTO 和数据损失 RPO 达标；演练有记录 |
| O-05 | P0 | 上传安全 | 文件大小、类型和魔数校验 | 接入对象存储、病毒扫描、图片重编码、访问域名隔离和容量限制 | 降低恶意文件与磁盘耗尽风险 | 对象存储和扫描服务增加成本 | 恶意样本被拦截；超限有告警；上传域与主站隔离 |
| O-06 | P0 | 供应链安全 | CI 执行构建和测试 | 增加依赖漏洞扫描、容器镜像扫描、SBOM、Secret 扫描和 Dependabot | 提前发现高危依赖与凭据泄露 | 需要处理误报和升级兼容性 | 高危漏洞阻断合并；依赖升级 PR 可追踪 |
| O-07 | P1 | 可观测性 | Docker 日志和健康检查 | 引入结构化日志、请求 ID、指标、错误追踪与告警；定义 SLI/SLO | 更快定位线上故障 | 指标平台和告警规则有维护成本 | 可从一次错误追到请求、用户动作和数据库调用 |
| O-08 | P1 | 数据库性能 | MyBatis、MySQL 与基础索引 | 根据慢查询日志优化复合索引、分页和查询计划；避免 N+1 | 降低文章和后台列表延迟 | 错误索引会增加写入成本 | P95 查询耗时下降；慢查询数量可度量 |
| O-09 | P1 | 搜索能力 | MySQL 标题/摘要查询 | 内容量较小时先用 MySQL FULLTEXT；达到规模阈值后评估 Elasticsearch/OpenSearch | 改善中文检索、相关性和高亮 | 搜索集群会显著增加复杂度 | 有真实语料的召回率、准确率和延迟基线 |
| O-10 | P1 | 缓存一致性 | Redis 文章缓存和热门排行 | 明确缓存键版本、TTL、失效策略、击穿保护和降级路径 | 降低数据库压力且减少脏缓存 | 复杂失效逻辑可能造成旧数据 | 发布/修改后缓存及时更新；Redis 故障时公开阅读可用 |
| O-11 | P1 | 前端体积 | 已按页面拆分，但主包仍有体积警告 | 进一步拆分 Element Plus、编辑器和管理端依赖；启用资源压缩分析 | 首屏加载更快 | 过度拆包会增加请求数 | 移动网络下 LCP、JS 体积和缓存命中率改善 |
| O-12 | P1 | 自动化测试 | 单元、组件、三视口 E2E 和 CI | 后端增加 Testcontainers 的 MySQL/Redis 集成测试；补充契约和失败注入 | 减少“内存测试通过、真实数据库失败” | CI 时间和资源增加 | 迁移、SQL、会话和故障降级在真实容器中通过 |
| O-13 | P1 | GitHub 治理 | 已有 CODEOWNERS、模板与 CI | 启用 main 分支保护、必需检查、至少 1 人 Review、禁止强推和自动删除已合并分支 | 降低误合并和 main 失效概率 | 小团队合并速度略慢 | 无法绕过 PR 直接写 main；必需检查真实生效 |
| O-14 | P1 | 审计与隐私 | 已记录关键管理审计 | 增加审计查询、保留周期、敏感字段脱敏、数据导出/注销流程 | 提升可追责性与隐私合规能力 | 需要明确政策和权限 | 管理动作可追踪；日志不含密码、Cookie、Token |
| O-15 | P2 | 高可用 | 单实例 MySQL、Redis 和应用 | 先通过监控证明需要，再采用托管数据库、Redis 哨兵/集群和多实例应用 | 降低单点故障 | 成本和运维复杂度显著增加 | 实例故障演练时业务达到目标 SLO |
| O-16 | P2 | CDN 与图片 | 图片由本机上传卷提供 | 图片生成多尺寸 WebP/AVIF，静态资源接入 CDN，配置缓存版本 | 减少带宽并改善移动端体验 | 需要图片处理与缓存失效 | 图片字节数、LCP、跨区域延迟下降 |
| O-17 | P2 | 内容协作 | 当前以单作者后台为主 | 增加文章版本历史、草稿协作者、审核流和定时发布 | 支持真正的编辑团队 | 权限和冲突模型复杂 | 多人编辑不覆盖；版本可比较和回滚 |
| O-18 | P2 | 限流策略 | Redis 按登录等关键动作限流 | 按接口风险分层，加入用户/IP/设备组合规则与可观测告警 | 抵御撞库、刷评论和滥用 | 误伤正常用户，需要白名单和申诉 | 压测时恶意流量受控，正常用户错误率可接受 |
| O-19 | P2 | 无障碍人工验收 | 已有 axe、键盘、200% 和 reduced-motion | 增加屏幕阅读器、焦点顺序、中文语义和真实低视力用户检查 | 覆盖自动扫描无法发现的问题 | 需要人工测试时间 | NVDA/VoiceOver 关键路径可独立完成 |
| O-20 | P3 | 产品分析 | 后台有业务数量看板 | 在征得用户同意后采集隐私友好的阅读与转化指标 | 用真实数据决定功能优先级 | 隐私、Cookie 和数据解释风险 | 指标定义透明、可退出，能支持明确产品决策 |

## 推荐实施顺序

### 阶段 A：准备公网前

1. O-01 HTTPS；
2. O-02 密钥管理；
3. O-03 生产配置；
4. O-04 备份灾备；
5. O-05 上传安全；
6. O-06 供应链安全；
7. O-13 GitHub 分支保护。

验收重点是“安全边界真实生效”，不能只看配置文件存在。

### 阶段 B：首批真实用户

优先 O-07、O-08、O-10、O-11、O-12、O-14。先建立指标基线，再优化；没有前后对比的数据，不应声称性能得到改善。

### 阶段 C：内容和流量增长后

根据慢查询、搜索失败、可用性和用户反馈决定是否执行 O-09、O-15 至 O-20。不要因为技术流行就提前引入搜索集群或高可用集群。

## 每项优化建议使用的决策模板

提出优化 Issue 时，至少回答：

| 问题 | 示例 |
|---|---|
| 当前问题是什么？ | 移动网络首页 LCP P75 为 4.2 秒 |
| 谁受到影响？ | 手机访问公开文章的读者 |
| 当前基线证据？ | Lighthouse、真实用户监控、后端 P95 |
| 建议改什么？ | 拆分编辑器依赖并延迟加载管理端 |
| 不做的后果？ | 首屏继续下载与读者无关的大包 |
| 风险与回滚？ | 新分包加载失败时回退前一版本 |
| 验收阈值？ | LCP P75 < 2.5 秒且 E2E 全通过 |
| 是否需要新凭据/成本？ | CDN 或监控平台可能产生费用 |

## 明确不建议的“伪优化”

- 没有指标就宣称“性能提升 50%”；
- 为了简历堆栈同时引入 Kubernetes、Kafka、Elasticsearch 和微服务；
- 关闭 CSRF、权限检查或文件校验来让测试更容易通过；
- 只提高缓存时间，却不设计发布后的失效规则；
- 只生成备份文件，从不执行恢复演练；
- 把生产密码写入 Compose、README、Issue 或 GitHub Actions 日志；
- 把静态页面截图当成真实前后端联通证据。
